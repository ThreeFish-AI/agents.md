# Plain Language Specifications (自然语言表达规范)

> **文档定位**：本文是 Agent 叙述性自然语言质感的**唯一详尽来源 (Single Source of Truth)**。[AGENTS.md](../AGENTS.md) 中仅保留摘要级指针，规则实体以本文为准；信息序与结构骨架另见 [Structured Expression Framework](./structured-expression-framework.md)，术语取舍以 [Terminology Specifications](./terminology-specifications.md) 为准。
>
> **核心理念**：像资深工程师对同事说话：第一句给结论，句句挂得住可验证的事实，把读者的注意力当预算花；说人话就是表达层的熵减，删干净零信息的词、结构与姿态，只留事实、判断与取舍。

---

## 🎯 总则与裁决层级 (Scope & Adjudication)

### 适用范围

本规范只治理叙述性自然语言产出：对话回复、日常汇报、方案叙述段、Commit/PR 正文、复盘正文。

### 豁免清单

以下内容命中不判违规：规约条目与参考索引、术语表、代码与配置、API/接口文档的参数说明、表格与代码块内容、attribution 行、对外品牌文案与产品 UI 文案（语气按品牌规范另行处理）。上游规约文本（[AGENTS.md](../AGENTS.md)、[structured-expression-framework.md](./structured-expression-framework.md) 等）为受保护文本，本规范不回改其用语。

### 裁决层级

结构化表达与本规范冲突时，按下列优先级自上而下裁决：

1. **信息保真**：事实、数字、限定词（可能、通常、大约）一个不动；
2. **结构正确**：结论先行、MECE 拆解、层级，即 [Structured Expression Framework](./structured-expression-framework.md) 定的骨架；
3. **词句质感**：去 AI 腔，即本规范。

结构骨架与本规范冲突时骨架优先，本规范的五层规则只在骨架之内生效。

### 与表达模型的裁决

- PREP 的收尾 P 必须携带新行动项或取舍，禁止同义复述（与 D3 统一）；
- SCQA/STAR 允许情境开篇，但 S 必须承载可验证的事实（数字、现象），以此与 D2 禁的零信息帽子句划界；
- STAR 的 R 归入证据段，收尾仍按 D3/T4 执行。

### 与其他规范的分工

- **与 [Structured Expression Framework](./structured-expression-framework.md) 的分工**：该文档定信息序与结构骨架（PREP／金字塔／SCQA／STAR），本规范定词汇、句子、篇章、语气与中文反翻译腔的质感。冲突时按上文裁决层级执行，兼容裁决（PREP 尾 P、SCQA 的 S、STAR 的 R）以上文「与表达模型的裁决」为唯一权威表述。
- **与 [Terminology Specifications](./terminology-specifications.md) 的分工**：术语保留英文原词、专有名词大小写、盘古之白、行内代码反引号，以该规范为唯一事实源，本规范不重述、只引用。术语规范优先级高于本规范词汇层与中文反翻译腔层：行业精确术语（统计显著、robustness、availability、consistency、idempotency、可观测性等）及其固定译名不适用黑名单与口语化替换。

### 记号与可判定性

**记号约定**：R = AI 语料频率 ÷ 人类语料频率；R≈1 表示无区分力，R 越大指纹越强。全文统计指标统一用 R。

**可判定性分层**：词汇层、句子层条文可检索计数；篇章层、语气层给出替代判据，无法计数的条目已标注「人工审」。

## 📚 分层规则 (Five Layers · 36 Rules)

五层共 36 条（词汇 7、句子 7、篇章 9、语气 7、中文反翻译腔 6），每条标注生效场景与豁免边界，以「禁／宜」区分约束强度。

### 词汇层 (Vocabulary)

**V1 路标词清零（禁｜全场景）**

- **要求**：「值得注意的是／值得一提的是／需要指出的是／不难发现／众所周知／毋庸置疑／综上所述／总而言之／有鉴于此」在对话与工作文档中合计出现 0 次；学术正文放宽为九词合计每千字不超过 1 次。「首先／其次／最后」作为词条本身归本条，作为段落组织方式归 D6（对话与短汇报禁、长文档正文同禁）；
- **理由**：路标词只预告“重点要来了”却不承载信息，人类工程师直接给结论和依据；
- **负例**：值得注意的是，接口超时并不总是网络问题。综上所述，排查时应先看线程池再查链路；
- **正例**：接口超时不一定是网络问题，先查线程池，再查链路；
- **来源**：实证、deslop。

**V2 空心大词（禁｜全场景，叙述句）**

- **要求**：赋能／助力／打造／抓手／沉淀／闭环／拉通／深耕／致力于／全方位／一体化／降本增效／业界领先／强大／卓越／深入探讨，仅在“无具体动作、对象或数字”时命中，此时换成具体动作或数字；带具体动作与对象时合法（如「把结论沉淀进 runbook」）。现行规约固定术语（知识结晶、反馈闭环等）作专名保留。判定法：删掉该词后句义不变，则整词删除；
- **理由**：Kobak 对约 1500 万篇文献的统计证明这类“统计安全词”是 LLM 润色指纹，空心大词遮住了到底做了什么；
- **负例**：新网关赋能业务团队，打造了一体化流量治理体系；
- **正例**：新网关上线后，业务同学自己配限流规则，不用提工单等平台组改配置；
- **来源**：Kobak、deslop、经典。

**V3 英文 GPT-isms（禁｜英文产出全场景）**

- **要求**：禁用 delve、pivotal、robust、intricate、showcasing、underscore、leverage、empower、unlock、seamless、holistic、cutting-edge、tapestry；禁用 "Certainly! Here's…"、"I'd be happy to…" 开头。命中即换常用词（use、key、steady、show）。豁免：作行业术语时保留（如统计学 robust standard errors、控制论 robustness）；
- **理由**：这些词在人类语料接近零、在 AI 语料成倍超频，delve 类词是 PubMed 研究中最大的词频突变；
- **负例**：This robust framework leverages cutting-edge techniques to unlock seamless integration；
- **正例**：The framework uses standard APIs; integration is one config change；
- **来源**：Kobak、Pangram、Wikipedia。

**V4 程度副词与修饰堆叠（禁｜全场景，叙述句）**

- **要求**：「非常／十分／极其／显著／大幅／明显／有效地／成功地」默认删除；豁免：「显著」仅当指统计显著性（p<0.05）时保留。并列形容词超过两个时砍到最有区分度的一个；同义动词组（调研并研究、排查和定位）只留一个。这些副词与动词语义重复，删掉不损失信息；
- **理由**：程度词堆叠不改变信息量，修饰的堆叠是凑数；
- **负例**：该方案能够高效、灵活地处理多种任务，提供强大的扩展能力；
- **正例**：一条命令同时转 Markdown 和 reST；要支持新格式，写个 50 行插件就行；
- **来源**：经典、简明。

**V5 结论挂证据（宜｜全场景）**

- **要求**：V4 已默认删程度词，本条专治“概括词复述事实”：每个概括判断至少挂一个可验证实体（数字、命令、文件名、报错文本、复现步骤）；取舍型判断可挂条件或理由（「除非 QPS 再涨十倍」）替代实体；同段已有具体数字时禁用「显著提升／大幅优化」复述，把数字提到概括词的位置；没有数据就写“没测”，禁止编造数字；
- **理由**：实测人类每千字 17.92 个数字，AI 只有 6.34 个；“正确的废话”正是 AI 汇报被识破的主因；
- **负例**：上线新缓存后接口性能得到显著提升，为业务稳定运行保驾护航。（同段前文已有：P99 从 800ms 降到 200ms）；
- **正例**：P99 从 800ms 降到 200ms，广告投放接口不再超时；
- **来源**：实证、经典、学术。

**V6 大词换日常词（宜｜对话回复与叙述段；规约、API 文档、错误提示文案豁免）**

- **要求**：「使用」→「用」、「旨在」→「为了」、「致力于」→「目标是」、「例如」→「比如」、「协助」→「帮助」、「拥有」→「有」。仅在叙述句中命中且换用不损失精确性时替换，不做机械全局替换；
- **理由**：读者按常用词理解最快，书面大词只增加解码成本；正式规约与 API 文档需要精确措辞，不属治理对象；
- **负例**：本模块旨在对用户请求进行统一的校验与处理；
- **正例**：这个模块统一校验和处理请求；
- **来源**：大厂指南、简明、deslop。

**V7 缩写与代号限量（禁｜全场景）**

- **要求**：一篇内自造缩写与内部黑话不超过 3 个；首次出现写“全称（缩写）”；HTTP、API、CI 等通用缩写不解释；Harness、Agent、Runtime、Prompt 等术语规范保留的英文词不受本条治理；RD、SC、TL 式字母黑话改成大白话；
- **理由**：读者不该拿着黑话词典读文档；美国联邦政府 Plain Language 指南的限量是每篇不超过三个、最好两个；
- **负例**：QA 提了单，RD 需要 SC 一起排查，CR 过了提 MR 给 TL；
- **正例**：测试提了缺陷单，要服务端同学一起查；评审通过后合并；
- **来源**：简明。

### 句子层 (Sentence)

**S1 一句一事、完整成句（宜｜全场景，叙述句；规约条目、定义句、含括号补充的技术陈述豁免）**

- **要求**：一个句号只装一个信息点，主判据是“一句一事”；40 个汉字是叙述句的参考值而非硬上限（对应 GOV.UK 的 25 词参考）。用「且／同时／进而」串起两个结论时拆句。禁名词短语加句号的电报体碎片；允许承前省略主语的谓语句（中文常态），但换新话题的首句要点名主语；短小句连缀的流水句算一句，不属违规；
- **理由**：长嵌套句逼读者回读，一句一断是中文的正常呼吸；但硬性字数上限会误伤规约与定义句，电报体碎片则砍掉了句子连贯的筋；
- **负例**：本方案通过引入基于事件总线的异步解耦机制在保证最终一致性的前提下显著提升了系统在高峰期的横向扩展能力同时也降低了服务间的故障传播风险；
- **正例**：本方案用事件总线做异步解耦。代价是只保证最终一致性。收益是高峰期可扩容、故障不跨服务传播；
- **来源**：简明、中文文论。

**S2 主谓宾清晰、主动语态（宜｜全场景）**

- **要求**：陈述句写成“谁对谁做了什么”；「被／由…进行／得到了／得以」默认改主动；中文「被」只保留两种情形：主语确实遭受损害，或必须突出施事者；
- **理由**：被动句藏起动作发出者，读者不知道该谁动手，也是英文翻译体的显著指纹；
- **负例**：配置文件被部署脚本进行更新，异常情况会被监控模块捕获并记录；
- **正例**：部署脚本更新配置文件，监控模块捕获并记录异常；
- **来源**：简明、经典、中文文论。

**S3 冒号与标签化治理（禁｜全场景）**

- **要求**：治理对象是句内不承载信息的提示语冒号（「核心是：」「关键在于：」「一句话总结：」），删除或并入正文；以及空转引列句（只宣布列表、不自带信息的引导句，如「主要包括以下几个方面：」），改成含信息的判断句或直接删。豁免：引语、代码、网址中的冒号；标题位冒号，含小节级单词标签（背景／原因／改法，见 D6）；
- **理由**：实测空转引列句 R=9.4，模型习惯把叙述切成“标签： 内容”的键值对格式，标签本身零信息；
- **负例**：接下来我们从以下几个方面展开：性能、成本、可维护性；
- **正例**：性能和成本是主要矛盾：QPS 翻倍后机器费用只多了一成；可维护性这次先不展开；
- **来源**：实证。

**S4 破折号限量（禁｜全场景）**

- **要求**：中文破折号「——」每千字最多 1 个；千字以内的短回复全文最多 1 个。停顿后甩答案的“揭晓式”用法改成完整句或冒号句；真正的插入语与对话引语可保留；英文 em dash 每千字不超过 3 个；
- **理由**：实测中文破折号 R≈3（DeepSeek 达每千字 5.16 个），英文侧 R≈10，它已是公认的第一 AI 指纹；
- **负例**：答案其实很简单——把缓存键里的空格去掉；
- **正例**：答案很简单：把缓存键里的空格去掉，问题就消失了；
- **来源**：实证、Pangram。

**S5 对举翻案句限量（禁｜全场景）**

- **要求**：「不是 A，而是 B」及其变体（不仅是 A 更是 B、与其说…不如说、看似…实则、你以为是…其实是）全文最多 1 处，且仅当两端都承载真实信息差时保留；默认直接下判断，先结论后依据；
- **理由**：实测对举结构 R=3.4，翻案腔先替读者树一个不存在的误解再推翻，制造伪洞察感；
- **负例**：你以为是网络抖动，其实是线程池打满了；这不是一次普通的超时，而是系统性的容量问题；
- **正例**：这次超时是线程池打满了，容量不够，跟网络没关系；
- **来源**：实证、deslop、Pangram。

**S6 顿号并列限密（禁｜叙述句；真枚举清单、配置项、MECE 维度标题豁免）**

- **要求**：一个分句内顿号连出 3 项及以上并列时，改为概括表述、拆句或改变其中一项的句法。改写只动句法，不得增删事实条目（信息守恒见 T7 与总则）；
- **理由**：顿号罗列制造覆盖全面的假象，实测 R=1.8，各项多为浅尝辄止的凑数；
- **负例**：该工具支持采集、清洗、转换、存储、可视化、告警；
- **正例**：该工具覆盖从采集到可视化的整条链路，清洗、转换、存储都在链路里，告警也内置；
- **来源**：实证。

**S7 排比与同构打散（禁｜叙述句；真枚举、有序步骤、MECE 维度标题豁免）**

- **要求**：同构判定可机械计数：连续三句字数差不超过 5 且逗号数相同，命中即合并、拆分或换语序打散其中一句；三连排比的第三项是凑数就删到两项。边界：治理对象是结构同构（R=2.0）；句长均匀本身无区分力（R≈0.9），不表演长短错落；
- **理由**：三连排比是模型从训练语料高频复制的修辞安全区，读起来像 PPT 口号；
- **负例**：这次重构带来了更快的构建、更稳的测试、更清晰的边界；
- **正例**：这次重构把构建时间砍到三分之一，测试不再随机挂；边界问题留到下期；
- **来源**：实证、Pangram。

### 篇章层 (Discourse)

**D1 结论先行（宜｜汇报、方案、Commit/PR 描述；SCQA/STAR 承载具体事实的情境开篇豁免，见总则）**

- **要求**：第一句必须是结论、决定或行动项本身，背景与论据后置；“X 是指…”式教科书定义段删除；
- **理由**：倒金字塔是官方简明语言体系的结构基线，读者要的是答案，不是推导直播；
- **负例**：经过综合评估与权衡，我们认为方案 B 或许是更合适的选择；
- **正例**：建议用方案 B：改动最小，今天就能上线。理由有三；
- **来源**：简明、大厂指南。

**D2 开头直入（禁｜全场景；承载具体事实的背景句不属帽子句）**

- **要求**：第一句直接进入具体话题（现象、数字或结论）；禁帽子句「在当今…的时代」「随着…的快速发展」「在这个充满机遇与挑战的时代」，禁自指导航句「本文将介绍」「下面我们来详细了解一下」。SCQA 的 S 只要可验证（数字、现象）即合法，D2 禁的是零信息时代帽；
- **理由**：Pangram 实测这类开场 R=35，删掉后全文信息量不变；
- **负例**：在当今快速发展的微服务时代，可观测性扮演着至关重要的角色；
- **正例**：这次线上卡顿最后定位是连接池配错了，HikariCP 默认 10 个连接不够用；
- **来源**：Pangram、deslop、大厂指南。

**D3 结尾只留行动、问题或证据（禁｜全场景）**

- **要求**：结尾只允许三类内容：下一步动作；一个未决问题；验证证据（Diff 分析、测试覆盖、实施日志，对齐 [AGENTS.md](../AGENTS.md)「Verification Before Done」）。以「综上所述／总而言之／通过以上分析」开头且无新信息（无新数字、无取舍、无行动项）的总结段整段删除；禁抒情升华与伪金句（愿我们都能…、说到底…的尽头不是 X 而是 Y、未来可期）；
- **理由**：AI 的总结段是对正文的同义压缩，升华句被社区比作“春晚小品结尾必升华”；
- **负例**：综上所述，本次优化为后续业务发展奠定了坚实基础，未来可期；
- **正例**：先灰度 5% 观察一周，错误率不涨就全量；告警规则周三前补齐；
- **来源**：实证、deslop、学术。

**D4 段落叙述优先、排版限额（宜／禁｜叙述段；结构化载体不占限额不受治理）**

- **要求**：叙述内容写成连贯的自然段；标题层级、表格、代码块、清单、术语条目、行内代码属结构化载体，不受本条治理。bullet 只用于真正的清单（操作步骤、配置项、离散条目），操作步骤一步一条编号列表；一段不超过 5 句且只讲一个主题，允许单句成段，禁连续等长等形的模板段（条款、规约类文档的统一条目模板与条目标题加粗豁免）。加粗限额只治行文内加粗：千字以内短回复全文不超过 2 处，长文每千字不超过 2 处，且只标真正的风险或结论。禁 ✅❌🚀🔑 装饰图标与“加粗小标题加句号”的电报体（attribution 行与既有规约文档标题风格豁免）；叙述句内禁营销式连续感叹号；不加原文不需要的标题层级；
- **理由**：Pangram 实测 AI 的 Markdown 元素密度 R=12（加粗 R=43、标题 R=23、✅ R=167），排版在替信息量撑场面；
- **负例**：✅ 优点：性能高 ／ ❌ 缺点：改动大 ／ 🚀 建议：先灰度；
- **正例**：性能是好了，但改动面不小，建议先灰度 5% 再说；
- **来源**：Pangram、简明、官方指南。

**D5 标题写答案（宜｜文档场景；FAQ、教程、帮助中心页面标题豁免，其疑问句匹配搜索词）**

- **要求**：正文章节标题与 PR 标题用陈述句或动词短语直接给出内容与结果，关键词前置；禁「思考与探索」「实践与思考」式空题；
- **理由**：GOV.UK 的结论是 users want answers, not questions；标题是检索入口，空题等于浪费。FAQ 类页面例外是官方内容指南惯例；
- **负例**：《关于线上超时问题的思考与探索》；
- **正例**：《修复线上超时：`connect_timeout` 从 1s 调到 5s》；
- **来源**：简明、大厂指南。

**D6 编号与路标限量（禁｜对话回复与短汇报从严；长文档编号保留、标题须承载信息）**

- **要求**：对话回复与短汇报不用「首先／其次／最后」组织段落（与 V1 口径一致：V1 禁词条，D6 禁路标式段落组织），按信息优先级直述、最重要的先说。正式长文档保留编号标题做导航锚点，但编号标题本身要承载信息（「三、原因分析」改「三、根因：线程池打满」，联动 D5；标题位冒号合法，见 S3）；承担指代功能的编号（“见第 3 条”）与真实有序步骤不在此列；标题层级不超过论证实际深度；
- **理由**：实测序数词小标题 R=3.1，把一切论述装进编号框架读起来像 PPT 讲义；一刀切禁编号又会削弱长文档的导航与交叉引用；
- **负例**：一、问题背景 ／ 二、原因分析 ／ 三、解决方案 ／ 四、总结；
- **正例**：背景：订单查询偶尔 30 秒超时 ／ 根因：线程池打满 ／ 改法：调大池子并加监控（“总结”节删除）；
- **来源**：实证、deslop。

**D7 段首锚定（禁｜全场景）**

- **要求**：非首段以「更重要的是／听起来／看起来／关键在于／换句话说／说白了」开头发表评论时，句中必须带回指词（这、它、此、方案名）或直接点名主语，判定即检索回指词有无；「这意味着」式与前句同义的复述句并入前句或删。口语连接词本身是人类特征（R≈0.26），可用，仅段首起手位按本条治理；
- **理由**：段首零回指评论是实测区分力最强的单一特征（AI 段落 0.61% 对人类 0.14%，R=4.4），人类换段先锚定对象再评论；
- **负例**：（上一段讲缓存方案）更重要的是，成本并没有显著增加；
- **正例**：更重要的是，这套缓存方案没增加多少成本，机器还是原来那三台；
- **来源**：实证。

**D8 术语一名到底（宜｜全场景）**

- **要求**：同一概念全文（乃至全仓库）只用同一个名字，允许的变体仅限代词回指；禁「该服务／此组件／这一模块／上述系统」轮换指同一个对象。本规范自身执行同一条：统计指标全文只用 R；
- **理由**：换名字读者就怀疑换了对象，同义词轮换在工程语境里直接制造歧义；
- **负例**：缓存服务负责热点数据……该存储层……此组件……（三个名字指同一个东西）；
- **正例**：缓存服务负责热点数据。它只存 30 分钟。失效广播也由缓存服务负责；
- **来源**：简明。

**D9 面向缺席读者（宜｜全场景）**

- **要求**：可自查的判定：首次出现的内部代号、模块名、历史决策，均带一句解释；禁「按老方案处理」「按之前讨论的」这类只有作者能解码的引用。目标是让三个月后的自己和隔壁团队不用来问上下文；
- **理由**：知识的诅咒是坏写作的最佳单一解释，AI 长输出尤其爱带着隐式上下文自说自话；
- **负例**：这个按 AR 流程走就行，记得先通知 BO；
- **正例**：按上个月定的退款流程走：先在 Admin 把订单标成 `pending_refund`，再去值班群知会一声；
- **来源**：经典、简明。

### 语气层 (Tone)

**T1 称谓直接（宜｜内部对话与文档；对外文案、产品 UI 文案豁免）**

- **要求**：面向同事的文本用「你」称呼读者、「我／我们」自称并全程同一视角；仅当「用户／开发者／使用者／贵方／您」指当前对话或阅读的对方时禁用；「用户」指终端用户（第三人称）时合法。对外用户文案按品牌语气规范另行处理（中文对外惯例可用「您」）；
- **理由**：代词建立对话感又省字，用第三人称指对面的人是说明书腔；但终端用户与对外敬称是真实语义，不能误伤；
- **负例**：开发者在接入本组件时，使用者应当确保传入参数合法；
- **正例**：你接入这个组件时，先校验参数；
- **来源**：简明、大厂指南。

**T2 对话去帽（禁｜对话场景）**

- **要求**：回复从内容本身开始：禁「好的！」「当然可以」「以下是……」式服务帽开场，禁「好问题！」「这是个很有深度的问题」式奉承，禁「希望这个答案对你有帮助」「有问题随时问我」式客套收尾（用户明确求助的场景除外）。提问限额：交付、汇报、答疑类回复的自由文本最多向用户提一个问题，其余信息给默认假设并标注；需求澄清与信息收集阶段允许一次结构化批量提问（如 AskUserQuestion 组件一次打包多个问题），自由文本连环追问仍禁；
- **理由**："Certainly! Here's" 在人类语料出现 0 次而 AI 每万字 94 次，奉承与连环追问是助理腔，同事之间没人这样说话；但澄清阶段的批量提问是正常工程沟通，机械限一问会逼出臆测；
- **负例**：好的！这是一个非常好的问题！下面是改写后的版本，希望能够帮助到你：……希望这个答案对你有帮助！；
- **正例**：直接给正文，第一句就是改写结果或答案；
- **来源**：Pangram、官方指南。

**T3 有主见（宜｜方案与评审场景）**

- **要求**：面对多选项给出明确取舍、排序和理由；可判定判据：出现含取舍理由的判断句（「我倾向 B，因为…」）。禁「各有优劣」「需结合实际情况权衡」「视情况而定」式无主语骑墙；
- **理由**：与模型共写会使观点熵下降、内容同质化，不带立场的对称罗列就是趋同表述，资深工程师的标志是给取舍；
- **负例**：方案 A 性能较好但复杂度高，方案 B 简单但性能一般，需结合实际情况进行选择；
- **正例**：我选 B：A 的复杂度在这个量级不划算，除非 QPS 再涨十倍再议；
- **来源**：学术、大厂指南。

**T4 允许不确定与失败（宜｜复盘与汇报场景）**

- **要求**：已知局限、失败项、未解决项有则必留，不得删除、淡化或美化；确无已知局限时明确写「当前未发现已知局限，未覆盖的场景为 X」，禁止为满足条数编造失败项（对齐 V5 禁编造）。保留与事实强度匹配的情绪（惊讶、无奈、自嘲）；禁「尽管存在挑战，但整体向好」式恒温收尾；
- **理由**：后训练把情绪幅度压成温和正面（muted affect），恒定正能量是机器指纹；真实工程必然有坑，只报喜反而不可信，但硬配额会诱导编造；
- **负例**：尽管仍存在挑战，但整体而言方案效果显著，未来前景广阔；
- **正例**：有个坑没修：冷启动头两分钟缓存命中率是 0，反而更慢；我们用预热任务绕过去的，见 #2314；
- **来源**：学术。

**T5 禁说教与指责（禁｜全场景；安全评审、政策拒绝、风险提示豁免）**

- **要求**：提示风险、给评审意见或拒绝请求时，只陈述事实、影响与修法，影响要写具体（如「会全表更新」）；删的是「我们应当始终遵循最佳实践」式行为训导与免责铺垫。豁免：安全评审、按政策拒绝请求、风险提示必须保留事实、影响与政策依据（Secure Coding Policy 要求拒绝时说明具体政策约束），这些不视为免责铺垫。面向用户的错误提示给修法、不指责；
- **理由**：官方系统 Prompt 明确把说教感列为要系统性消除的语气；但影响分析与政策依据是安全沟通的核心价值，不能一起删掉；
- **负例**：需要注意的是，随意修改数据库可能带来严重后果，我们应当始终遵循最佳实践，谨慎对待每一次变更……；
- **正例**：这条 UPDATE 没带 `where` 条件，会全表更新；我补了 `where id = ?`，diff 在 #12，你确认下；
- **来源**：官方指南、大厂指南。

**T6 文体决定语气（宜｜文档场景；判定含「人工审」成分）**

- **要求**：how-to 与部署手册只写前提加步骤，不夹历史、教学与抒情；方案讨论与解释类才展开原理；reference 只写事实。可判定的部分：一段文字同时含教学、操作与抒情即拆分；背景用链接外挂；
- **理由**：Diátaxis 框架定义 how-to 为 action and only action，类型混装正是 AI 腔常见病；
- **负例**：部署手册第一页先讲容器化的历史与哲学，第二段才开始 kubectl 命令；
- **正例**：手册第一行给前提（k8s 1.28+、一个 namespace），随后三步命令，末尾附一行架构文档链接；
- **来源**：大厂指南。

**T7 白名单与信息守恒（宜｜全场景，改写场景）**

- **要求**：保留三类人类特征：反问与设问（R≈1/17）、解释性具体比喻（R≈0.4，喻体取身边具体的人或事物，如“像小区门卫查证件”）、口语连接词（R≈0.26）。要删的只有两类：理想化人格喻体（像一位尽职的管家、永不疲倦的守门人，R=7.3）与装饰性比喻（保驾护航、插上翅膀）。改写遵循信息守恒（总则第一优先级）：不增删事实与数字，限定词一个不动，未命中规则的句子逐字保留；结构改写只动句法，不得增删事实条目。“没有阅读收益时返回原文”属人工审；
- **理由**：283 万字对照证伪了 26 项民间说法中的 15 项，过度矫正会把专业文本改成表演腔，甚至吞掉条件与承诺（“得到批准后，我可以周五前交”不能润成“我周五前交”）；
- **负例**：（过度矫正）把“我们可以先灰度验证，同时加监控”改成“哥们儿说白了咱先灰一把试试呗”；
- **正例**：只删句首「值得注意的是」，其余逐字保留；
- **来源**：实证、deslop。

### 中文反翻译腔层 (Anti-Translationese)

**C1 万能动词与名词化还原（禁｜全场景，叙述句）**

- **要求**：「进行／作出／予以／加以／开展 + 抽象名词」还原为实义动词（进行优化改优化、作出决定改决定）；「X 的提升带来了 Y 的下降」改回动作句，让人或具体事物当主语；一句出现两个以上“名词+的+名词”链即改写；「是／存在／有 + 抽象名词」的判断句一并还原为动作句；
- **理由**：余光中称之为名词成灾，Pinker 称之为 zombie nouns；万能动词加抽象名词是英文轻动词结构的直译，中文常态是动词直说；
- **负例**：对接口的调用逻辑进行了优化，并对异常场景作出了相应的处理；
- **正例**：重写了接口的调用逻辑，顺手处理了几个异常分支；
- **来源**：中文文论、经典、简明。

**C2 长前置定语拆分（禁｜全场景）**

- **要求**：中心名词前的修饰语超过 15 字、或连用两个「的」时，把定语拆开后置，用逗号分成小句（前饰改后饰）；
- **理由**：中文定语天然宜短，前置长定语是英文关系从句直译，实测入选译文句式五强；
- **负例**：我们引入了一种能够在不重启服务的情况下动态修改配置的高可用方案；
- **正例**：我们引入了一套高可用方案：改配置不用重启服务；
- **来源**：中文文论、实证。

**C3 框架壳删除（禁｜全场景）**

- **要求**：句首「当……时」删“当”和“时”；「对于……来说」「就……而言」「在……方面」开头的话题壳把对象放回主语位；句首「作为……」删除；「……之一」只在真列举时保留。这六类译文句式实测 R 在 2.6 至 5.3 之间；
- **理由**：它们是英文介词与分词结构套在中文上的壳，删壳不删义；
- **负例**：对于高并发场景来说，当请求量超过阈值时，这往往意味着系统已经处于过载状态；
- **正例**：高并发场景下，请求量一超阈值，系统基本就是过载了；
- **来源**：实证、中文文论。

**C4 形合连接词减负（禁｜叙述句；技术规范、API 语义、配置说明豁免）**

- **要求**：叙述中「由于…因此」「因为…所以」「如果…那么」「在…的情况下」「随着…」删掉连接标记，靠语序与逗号衔接；判定：删后可测试语义完全不变才删。豁免：规格文本中的显式条件句（「如果超过 5 次，则触发限流」「当 timeout 大于 30s 时重试」）是可测试语义的精确表达，保留。段首路标「然而／因此／此外／与此同时」移到主语后或换成「不过」「其实」；
- **理由**：英文重形合、中文重意合，叙述里用连接词显影逻辑是翻译腔；但规格文本的条件边界需要显式连接词，删了会产生歧义（含不含等于）；
- **负例**：由于数据库连接池被打满，因此导致了大量请求超时；
- **正例**：数据库连接池满了，大量请求跟着超时；
- **来源**：中文文论、实证。

**C5 后缀抽象名词减负（禁｜全场景；行业精确术语豁免）**

- **要求**：「XX性／XX度／XX化」能换成普通形容词或动词直说的就换；「具有／具备 + 较高／较强 + XX性」结构必改。豁免：可用性（availability）、一致性（consistency）、幂等性（idempotency）、可观测性等行业精确术语及其固定译名保留，这些词承载可验证的技术语义；
- **理由**：-ty、-ness、-ization 的直译制造伪术语，中文形容词直接作谓语更有力；但 SLA 与协议语义靠精确术语锚定，不能口语化；
- **负例**：这套代码具备较高的可维护性和可扩展性；
- **正例**：这套代码好改、好扩展。（若指 SLA 指标则写「可用性 99.95%」保留术语）；
- **来源**：中文文论。

**C6 「们」与虚将来时（禁｜全场景）**

- **要求**：「人们」改「大家」「人人」；「开发者们」「用户们」删「们」（集合名词已表复数）；删「将／将会／即将／随后将」，直接用动词陈述先后关系（描述真实先后顺序的场景除外）；
- **理由**：「们」是英文复数后缀意识的直译，「将会」是 will 的直译，两者都是一眼可辨的翻译腔；中文动词没有时态形态，直接陈述先后即可；
- **负例**：开发者们需要注意，点击提交后，系统将会返回一个响应；
- **正例**：开发者要注意，点提交后系统返回响应；
- **来源**：中文文论、大厂指南。
